# Standards and measurement reference

Research status: **2026-09-14**. This register identifies primary references for evaluating software products, their use, and their delivery. It complements the practical measures in [the industry scorecard](industry-scorecard.md) and the executable checks in [deterministic tools](deterministic-tools-2026.md). It is a research reference for the proposed [evaluation contract](design.md#evaluation-contract); v-eval has no implemented standards assessment or production runner.

The useful starting point is a versioned requirement with an appropriate measurement method. “Uses ISO terminology,” “a scanner found no issues,” and “meets this user's requirement” describe different claims. A standard can supply a vocabulary, measurement definition, or verification requirement; the project must still establish applicability, collect evidence, and state its acceptance rule.

## Interpretation details that affect an evaluator

**Pin editions before mapping rules.** The product-quality and quality-in-use models have separate 2023 publications. The 2016 measurement standards predate that split; this review does not assert that their measures map unchanged onto the newer models. The ISO catalogue also distinguishes a published edition marked for revision from its draft successor. Record both the edition used and any known transition; a draft's existence does not silently replace the evaluation contract. [ISO 25010](https://www.iso.org/standard/78176.html), [ISO 25019](https://www.iso.org/standard/78177.html), [ISO 25023](https://www.iso.org/standard/35747.html).

**Keep familiar concern names separate from official taxonomy.** Teams may ask about usability, portability, maintainability, or testability without referring to a particular edition. Preserve that requirement in their language, then record a verified mapping if needed. Avoid copying an older quality-model diagram and presenting it as the 2023 model. This document does not reproduce normative definitions that were not inspected.

**Separate measurement from acceptance.** A measure needs a definition, units, denominator or population, environment, collection method, and interpretation. The applicable project sets an acceptance rule unless a verified requirement supplies one. A configurable complexity ceiling is a local policy; it becomes misleading when described as “the ISO passing score.” ISO's public measurement overviews explicitly do not prescribe universal grading ranges. [ISO 25023](https://www.iso.org/standard/35747.html), [ISO 25022](https://www.iso.org/standard/35746.html).

**Preserve the level of evaluation.** Product structure, user effectiveness, development practices, and service outcomes require different evidence. DORA's current five-metric model also uses failed deployment recovery time, a narrower concept than recovery from every kind of outage. Comparing results collected under different definitions can create an apparent improvement without a matching operational change. [DORA history](https://dora.dev/insights/dora-metrics-history/).

**Use stable source identities.** OWASP recommends version-qualified requirement references. Its moving `latest` GitHub release had a September 2026 timestamp when checked; the fixed 5.0.0 release remains dated May 2025. Record the stable release and exact requirement instead of treating an updated download or page as a new standard edition. [OWASP project](https://owasp.org/www-project-application-security-verification-standard/), [5.0.0 release](https://github.com/OWASP/ASVS/releases/tag/v5.0.0_release).

## Proposed mapping into v-eval

The following are **project design proposals**, not prescribed standard checklists. They show how broad concerns become reviewable evidence. Detailed formulas and tradeoffs belong in [the industry scorecard](industry-scorecard.md).

| Concern in the user's brief | Candidate evidence and scope | Acceptance decision to make explicit |
| --- | --- | --- |
| Functional correctness and effectiveness | Requirement-linked behavior tests; representative user-task outcomes where actual use matters. | Which outcomes, inputs, participants, and contexts count; whether execution or user observation is required. |
| Performance and efficiency | Benchmarks or service measurements with workload, hardware, resource use, and measurement window. | Project latency/resource targets and tolerated regression; distinguish code execution time from human effort. |
| Maintainability, testability, and debuggability | Structural analysis, change review, test isolation and fault-detection evidence, diagnostic traces, and a realistic investigation task. | Specific maintainability risks or investigation outcomes; no default composite score equating shorter code with better design. |
| Security and reliability | Applicable versioned controls, threat-informed tests, failure/recovery tests, and observed service indicators. | Required controls, tested failure conditions, remaining uncertainty, and locally agreed service targets. |
| Accessibility and interaction | Applicable WCAG criteria, keyboard/assistive-technology review, and task-based human evaluation. | Evaluated pages, states, complete processes, criteria, and which checks need human judgment. |
| Compatibility and portability | API/format conformance checks and a stated operating-system, runtime, browser, or integration matrix. | Supported environments and interoperability behavior; a pass on one environment supplies evidence only for that scope. |

For each selected criterion, retain the requirement source, edition and identifier, applicability reason, evaluation method, actual evidence, tool/environment version, and threshold origin. Keep observed findings separate from uncertain interpretations. If the required method was unavailable, use the project's **UNKNOWN** or **ERROR** result rather than promoting a catalogue citation into a PASS. If a criterion is excluded, record the contract-defined reason.

Begin with the user's existing requirements and tests. Add applicable references when they make a requirement clearer or reveal a missing quality concern. Future adapters can ingest structured findings and operational measurements; they must preserve provenance and scope. A report should state exactly what was assessed and supported, without implying standards certification from the presence of these references.
