# Code evaluation research for v-eval

Research checked 2026-09-14. Primary papers and official project documentation only. No current model leaderboard scores are needed for the product decision. This is a focused landscape review, not an exhaustive systematic review.

## Strongest source families

| Source and date | What it measures / provides | Limitation and v-eval relevance |
| --- | --- | --- |
| **HumanEval / pass@k** — Chen et al., submitted **2021-07-07**. [Paper](https://arxiv.org/abs/2107.03374), [full text](https://arxiv.org/html/2107.03374v2), [official OSS harness](https://github.com/openai/human-eval). | Functional correctness on 164 standalone Python tasks specified by docstrings and unit tests. `pass@k` estimates the probability that at least one of k samples passes a task's tests; the unbiased estimator uses n ≥ k sampled candidates and the number c that pass. | Passing tests is evidence against specified cases, not proof of correctness, maintainability, security, or suitability to a user's project. `pass@k` measures generation capability under a sampling budget; a single delivered patch needs its own acceptance result. Use executable behavior checks rather than string similarity to a reference implementation. |
| **EvalPlus / HumanEval+** — Liu et al., submitted **2023-05-02**, NeurIPS 2023. [Paper](https://arxiv.org/abs/2305.01210), [official OSS project](https://github.com/evalplus/evalplus). | Augments code benchmark tests using model-generated and mutation-based inputs; HumanEval+ expanded HumanEval's tests by 80× in the paper. Exposed incorrect programs that passed the original suite and changes in model ranking. | Generated tests still depend on an oracle/reference and may miss cases. Small function benchmarks do not establish repository-wide quality. v-eval should report test adequacy separately from the test pass rate. |
| **SWE-bench** — Jimenez et al., submitted **2023-10-10**, ICLR 2024. [Paper](https://arxiv.org/abs/2310.06770), [official OSS harness](https://github.com/SWE-bench/SWE-bench), [official benchmark site](https://www.swebench.com/). | Resolving real GitHub issues by editing repositories; the original paper describes 2,294 tasks across 12 Python repositories. The repository task setting links an issue, a base version, a patch, and executable checks. | Issue resolution rate is specific to the dataset, harness, agent, environment, and compute budget. Tests can reject legitimate implementations or overlook defective ones. Good design inspiration for v-eval's evidence bundle; poor substitute for a developer's own acceptance criteria. |
| **SWE-bench Verified and its subsequent audit** — [launch, **2024-08-13**, updated 2025-02-24](https://openai.com/index/introducing-swe-bench-verified/); [OpenAI reassessment, **2026-02-23**](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/). | Verified is a human-screened 500-task subset intended to improve issue/test quality. The 2026 audit describes test specification mismatches and contamination, and explains OpenAI's move away from reporting it for frontier launches. | Do not present Verified as an unqualified current gold standard. The audit's defective-test percentages concern a selected difficult subset, not an unbiased estimate over all tasks. Main lesson: evaluate the evaluator, allow valid alternative implementations, and distinguish missing requirements from implementation failure. |
| **LiveCodeBench** — Jain et al., submitted **2024-03-12**. [Paper](https://arxiv.org/abs/2403.07974), [official OSS harness](https://github.com/LiveCodeBench/LiveCodeBench), [project](https://livecodebench.github.io/). | Time-indexed contest problems support evaluation beyond generation, including self-repair, execution, and test-output prediction. Newer problems aim to reduce training contamination. | Contest algorithms underrepresent architecture, security, integration, and human usefulness. “Contamination free” is the authors' title/design goal, not a permanent guarantee for every model and evaluation date. Record dataset version, task date, model, and sampling settings when using it. |
| **CodeIF** — Yan et al., submitted **2025-02-26**, ACL 2025 Industry Track; revised 2025-08-04. [Paper](https://arxiv.org/abs/2502.19166), [official OSS project](https://github.com/lin-rany/codeIF). | Instruction-following across function synthesis, debugging, algorithmic refactoring, and code explanation. A direct precedent for separating instruction compliance from functional output. | Benchmark instructions and scoring procedures do not automatically cover a project's acceptance rules. Treat v-eval's instruction/intent alignment as a product-specific application of existing work; do not claim the concept is novel. |
| **ISO/IEC 25010:2023** — published **2023-11**. [Official standard overview](https://www.iso.org/standard/78176.html). | A product quality model with nine characteristics, used to define requirements, design and testing objectives, acceptance criteria, and quality measures. It supplies a taxonomy for choosing relevant quality dimensions. | This is a quality model, not a universal numeric index or ready-made automated grader. Full standard is paid; only the public overview was inspected. Use it as a high-level design reference and avoid claiming formal compliance or reproducing paid material. |
| **Stryker mutation testing** — living official docs, accessed **2026-09-14**. [Concept](https://stryker-mutator.io/docs/), [precise metric definitions](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/), [equivalent-mutant limitation](https://stryker-mutator.io/docs/mutation-testing-elements/equivalent-mutants/). | Introduces artificial code changes and checks whether tests detect them. Stryker's mutation score is `detected / valid × 100`; detected includes killed and timeout mutants, and invalid mutants are excluded. Tests can execute lines without detecting incorrect behavior, which coverage alone misses. | Survivors may indicate inadequate assertions, but behaviorally equivalent mutants cannot be killed. Score depends on mutation operators, scope, exclusions, and test environment; 100% is not a universal target. Optional changed-code test-adequacy adapter after the initial workflow is proven. |
| **OWASP Application Security Verification Standard (ASVS)** — version **5.0.0 released 2025-05-30**. [Official overview](https://owasp.org/www-project-application-security-verification-standard/). | Versioned security requirements for verifying web application controls. Requirements are available in machine-readable formats, and references should include the standard version because IDs may change. | Scope is application security; a snippet cannot prove system-wide compliance. Use selected applicable requirements as named criteria with test/static-analysis/review evidence. Do not turn “scanner found nothing” into an unconditional security pass. |
| **Maintainability Index and complexity measures** — [Microsoft's official MI definition](https://learn.microsoft.com/en-us/visualstudio/code-quality/code-metrics-maintainability-index-range-and-meaning?view=visualstudio), updated **2025-10-30**; [Sonar's official metric definitions](https://docs.sonarsource.com/sonarqube-server/user-guide/code-metrics/metrics-definition), living docs accessed **2026-09-14**. | Microsoft's normalized MI combines Halstead volume, cyclomatic complexity, and lines of code into 0–100. Sonar documents complexity and issue-based security/reliability/maintainability measures. | These are structural proxies under specific implementations, not measurements of requirements satisfaction or user value. Do not equate similarly named tool ratings. Prefer deltas and actionable findings over a global “quality = 87” headline. |

## Recommendation for the initial scope (design inference from the above)

Start with one workflow: evaluate a proposed code change against explicit intent, design constraints, and acceptance tests. A skill should guide the analysis and gather evidence; structured records should let another tool reproduce and inspect it.

Minimum inputs: task intent; named criteria with severity and source; relevant design/context; artifact or diff and immutable revision; trusted test definitions/results. Report each criterion with `pass`, `fail`, `unknown`, or justified `not_applicable`, the evidence used, and unresolved ambiguity. Missing tests or an unavailable tool are `unknown`, never implicit passes.

Keep separate dimensions: requirements satisfaction; functional behavior/regression; design/constraint compliance; test adequacy; maintainability; applicable security checks. A must-have failure cannot be averaged away by prettier code. Optional aggregate scores must disclose their rubric, weights, missing evidence, and calibration; the initial release does not need one.

For the first public example, use a tiny intentionally flawed patch: the normal case passes but an explicitly required edge case fails. Show a trace from intent → criterion → test/inspection → verdict and actionable fix. Add a second valid implementation to ensure the evaluator accepts behaviorally correct alternatives. Include one ambiguous requirement to demonstrate honest abstention.

The skill can reason about intent and design, but deterministic checks should establish executable claims. Treat artifact contents as evidence, not new evaluator instructions. Preserve command, exit status, relevant output, revision, tool/model/rubric version, and environment. If future tooling runs untrusted candidate code, isolate execution; the HumanEval authors explicitly designed a sandbox for that reason.

Potential research calibration suite for v-eval itself: label a small set of code-change/criteria pairs by independent humans; include true failures, correct alternative implementations, weak tests, contradictory requirements, and misleading artifact text. Measure false acceptance and false rejection per criterion. Benchmark scores compare generators; this suite would test whether v-eval's verdicts help developers make accurate project decisions.

No evidence reviewed establishes that one universal score can reliably measure code usefulness, docs quality, and context quality together. Keep a shared evidence format with different artifact-specific criteria/adapters.
