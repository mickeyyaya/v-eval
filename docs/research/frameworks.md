# Evaluation framework landscape for v-eval

Research checked 2026-09-14 against official project repositories and documentation. This is a bounded feature comparison, not a benchmark or a maintenance audit. License labels below describe the linked files on the current default branch; individual bundled datasets and optional services can have different terms.

## Main finding

The promising product is a convenient developer workflow that turns an explicit intent/design/test contract into a reviewable acceptance report for a concrete artifact or repository change. Generic rubric scoring, mixed mechanical and LLM evaluation, evidence explanations, agent tracing, and CI gating already exist. The closest discovered prior art is **PlexusOne structured-evaluation**, which explicitly models requirement traceability, semantic/deterministic/human evaluation methods, blocking criteria, and evidence rules. These concepts should be acknowledged and evaluated for interoperability, rather than presented as inventions. [Rubric design](https://github.com/plexusone/structured-evaluation/blob/main/docs/features/rubrics.md), [implemented Go types](https://github.com/plexusone/structured-evaluation/blob/main/rubric/rubric.go).

## Comparison

“Custom” coverage means an application-specific evaluator can be written; it does not mean that an off-the-shelf repository acceptance workflow was verified.

It is relevant to measuring models against task suites, less directly to checking one developer artifact against one explicit specification. [Official overview](https://huggingface.co/docs/lighteval/index).

## Six design recommendations

The recommendations below are product/engineering inferences from the comparison, not features claimed absent from all other projects.

1. **Start with one inspectable unit: a repository change plus its acceptance contract.** Inputs should reference the intent, design decisions, requirement IDs, changed files and executable checks. Require explicit criteria before scoring, and preserve ambiguities as unresolved questions. Begin with code and accompanying documentation; add open-domain content/RAG packs after the basic workflow is useful. This tests the user's actual idea more directly than another model leaderboard.

2. **Build a small acceptance/evidence layer, with a skill as its interface.** Keep contract parsing, schema validation, evidence collection and decision aggregation deterministic. Let the skill help draft criteria and run the workflow. Compare structured-evaluation's schema before inventing one, and prototype one adapter to promptfoo or DeepEval instead of writing every evaluator/provider integration. The upstream examples show substantial overlap already. [Structured types](https://github.com/plexusone/structured-evaluation/blob/main/rubric/rubric.go), [promptfoo assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/).

3. **Make evidence mechanically checkable where possible.** For each criterion, record artifact/commit hashes, exact file/range or source references, the check command, tool version, exit status, timestamps and log artifact. Mark test results as observed only when actually run or imported from a trusted run. Bind semantic judgments to cited excerpts and reject broken references. Report `pass`, `fail`, `unknown` and `error` distinctly; do not convert missing evidence into a pass or an ordinary zero score. This is a concrete specialization to validate, not an established novelty claim.

4. **Separate acceptance gates from subjective quality dimensions.** A failed required test or unmet mandatory requirement should not disappear inside an average with strong prose scores. Show per-criterion status, coverage and optional dimension scores; make any aggregate policy explicit. Existing frameworks already support custom scoring/blocking; use that precedent rather than inventing a universal “meaningfulness index.” [Structured rubric methods/gates](https://github.com/plexusone/structured-evaluation/blob/main/docs/features/rubrics.md), [promptfoo scoring](https://www.promptfoo.dev/docs/configuration/expected-outputs/).

5. **Evaluate the evaluator before promising reliability.** Create a small human-labeled set of accepted/rejected code changes and documents with seeded omissions, misleading comments, failing tests, unsupported citations and irrelevant but fluent answers. Track false acceptance, false rejection, abstention and judge agreement; pin rubric/model versions and check repeatability after changes. DeepEval recommends explicit evaluation steps for more controlled scoring, and TruLens calls for validation against human labels and revalidation after rubric/model/threshold changes. [G-Eval](https://deepeval.com/docs/metrics-llm-evals), [TruLens feedback guidance](https://www.trulens.org/component_guides/evaluation/).

6. **Keep execution and data handling explicit.** Evaluated code and document content are untrusted inputs to the evaluator. Isolate executable checks with bounded time/resources and deliberate networking; store reports locally by default and make model/cloud submission visible in configuration. Do not rely on a skill prompt as the execution boundary. Inspect documents sandbox configuration and its limits, while promptfoo explicitly says its custom code is not sandboxed. [Inspect sandboxing](https://inspect.aisi.org.uk/sandboxing.html), [promptfoo security model](https://github.com/promptfoo/promptfoo/security).

## Positioning hypothesis worth testing

“v-eval helps developers decide whether an AI-produced change satisfies their stated intent: every criterion has a result, supporting evidence, and a reproducible check where possible.”

The defensible value would be fast setup in real repositories, accurate requirement-to-test/artifact mapping, verifiable evidence, clear unknowns and repeatable review. A skill wrapper or another LLM rubric alone is insufficient differentiation. Validate this by comparing completion time and false acceptance on the same real tasks using v-eval versus a hand-written promptfoo/DeepEval suite and structured-evaluation reports. Do not claim superiority until that comparison exists.
