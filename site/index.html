Evaluating AI-generated work

Don't trust the summary. Verify from the context.

v-eval is a skill for any tool-capable assistant, backed by a small Go core. It evaluates a code change, a document, or a generated context against the intent, design, sources, and acceptance criteria that define success: every claim checked against the underlying material, every verdict derived from evidence, a forensic pass for gaming traces on every evaluation.

№ 01 — the problem

The summary is not the work.

An assistant that wrote a change also writes its description. "All tests pass." "Follows the design." "No new dependencies." A reviewer who reads the description instead of the diff accepts whatever the author believed, or wanted believed. The same assistant, asked to grade its own work, tends to find it good.

v-eval takes the opposite stance. The description is a set of claims. Each claim is verified from the context it points at, or marked unverified. What the evaluator itself opened, ran, or cited is evidence; what it was told is not.

№ 02 — the rule

Evidence first. Verdicts derived.

A criterion can PASS only on evidence the evaluator observed, and only when that evidence points somewhere a reader can go: a file with a line range, a command with its exit status and log, or a passage with its source and dates. A note such as "the author says so" is a valid record of what was supplied, and it can never carry a PASS. The core enforces this; a report that breaks it is rejected before it is rendered.

Evidence hierarchyobserved execution > observed inspection > supplied logs > the candidate's own summary. Candidate-supplied material is labelled (supplied) everywhere it appears.
  1. IntakeEverything available is input: the brief, the artifact, the diff, the design, test definitions, execution records, prior reviews, the candidate's claims.
  2. ContractThe acceptance criteria become an explicit contract: identifier, requirement, source, required or optional, allowed methods, acceptance rule. Provisional criteria are marked and block acceptance until confirmed.
  3. Classify and routeThe evaluator records which perspectives and checks apply in this host, what was skipped, and why. Test evidence is one route to evidence among several, not the whole method. A deterministic classifier and adapters in the core are designed, not yet built.
  4. Collect evidenceFiles are opened, commands are run where the environment allows, sources are read. Each record carries its kind, its isolation level, and its provenance.
  5. Forensic passThe detective work: tests or graders touched alongside the change, provenance that does not match the artifact, hard-coded answers and special cases. Each finding carries a benign alternative and a disposition.
  6. DecidePer-criterion results, then one overall status by one auditable rule. No composite score.
  7. ReportCanonical JSON, validated by the core; Markdown and a self-contained HTML page; SARIF for tools that read it.

№ 03 — the states

Five states, one auditable rule.

Each criterion ends in exactly one of five states. UNKNOWN is a first-class answer: when the tests were not supplied, the honest result is that nobody knows, not that they probably pass. ERROR is reserved for a check that was actually attempted and could not complete.

The overall status follows from the required, applicable, confirmed criteria by a fixed order of rules, and the report names the rule it applied and the criteria that blocked acceptance. Change a result by hand and the core notices: the recomputed status and the stated one must agree, and so must the report's content hash.

StateMeansNeeds
PASSThe acceptance rule was metObserved evidence with a qualifying locator
FAILThe rule was not metEvidence of the failure
UNKNOWNCould not be determinedA next action that would settle it
ERRORA check ran and brokeThe attempt on record: execution evidence or a failed command
NOT_APPLICABLEDoes not apply hereReasoning that says why

PASS, ERROR, and NOT_APPLICABLE are enforced by the core; FAIL and UNKNOWN are the skill's obligations.

№ 04 — the detective pass

Verifying the known result is only the first step.

A change that makes the tests pass by changing the tests has passed nothing. A benchmark number quoted from a pull request description has been measured by nobody the evaluator can name. v-eval's forensic pass looks for exactly these traces: grader and test tampering, provenance that does not bind to the artifact under review, hard-coded outputs that satisfy the known cases and nothing else.

Isolation is recorded, not demanded. A check that ran in a clean worktree or a container says so; one that ran in place says that instead. The report never pretends a stronger setting than the one it had. And the evaluator is not an auditor handing down a verdict: it collects everything, shows what it found, and lets the verdict follow.

Fig. 2 — a findingextended example, F1

suspicious open  detector mtime-drift 0.3 on E6

Modification time 2026-09-14T00:04:12Z, after the evaluation started at 2026-09-14T00:03:00Z. A tracked file's modification time moved during the evaluation, and no pre-evaluation tree digest was recorded, so whether the artifact changed cannot be settled either way.

Benign alternative: a checkout or a formatter touched the file without changing its contents. Next action: record a tree digest before evaluation begins, then re-run and compare. The detector name and version are the fixture's; the core ships no detectors yet.

№ 05 — the report

One canonical record, three renderings.

The JSON report is the record: a published schema, canonical bytes, a content hash, and a digest over every piece of evidence. Markdown and HTML are renderings that add nothing. SARIF 2.1.0 carries the same results to any tool that reads it. The HTML is a single file with no script and no external resource, readable offline, in light and dark, on a phone or on paper.

veval version
veval aggregate report.json -o report.json
veval validate  report.json
veval render --format html report.json -o report.html
veval render --format md   report.json -o report.md
veval export sarif report.json -o report.sarif.json

Exit 0 when the report is sound, 1 when a rule is broken, 2 when the tool could not run. A report the skill wrote by hand goes through aggregate first, which fills the counts, the status, and the digests from the results; nothing else is derived by the assistant.

See the real thing rather than a description of it. Both example reports are rendered from the repository's fixtures by the current code when this page is deployed:

  • Code review: the deduplication change from Fig. 1, three failures and an unverified claim.
  • Service change: command and passage locators, an optional criterion, an error, a suspicious finding, an unresolved contract conflict.

№ 06 — where it runs

One skill, every CLI.

The skill is a SKILL.md workflow with a reference file per host that maps its seven actions (read a file, search, list, run a command, fetch a URL, dispatch a subagent, invoke the core) onto that host's tools. Where a host cannot run commands, execution criteria stay UNKNOWN and the report says so.

  • Claude CodeRead, Grep, Glob, Bash, WebFetch, Agent
  • Codexshell tool and spawn_agent; other actions from the session's own tool list
  • Gemini CLIfile, search, shell tools
  • Antigravityinvoke_subagent; other actions from the session's own tool list
  • Hermesits agent tool set
  • ollama-backed agentsthrough a harness such as Claude Code, Codex, or OpenCode

№ 07 — install

One line for the skill. One archive for the core.

The skill installs with the cross-agent skills installer into your project, or with -g into your user directory. Without it, copy skills/evaluate-output/ into your agent's skills directory.

npx skills add mickeyyaya/v-eval -y

The core is a static binary per operating system and architecture. Download the archive for your platform from the release, check it against checksums.txt, and put veval on your PATH. The skill calls it when present and states in the report when it is not.

curl -sSLO https://github.com/mickeyyaya/v-eval/releases/latest/download/veval_darwin_arm64.tar.gz
curl -sSLO https://github.com/mickeyyaya/v-eval/releases/latest/download/checksums.txt
shasum -a 256 --check --ignore-missing checksums.txt
tar -xzf veval_darwin_arm64.tar.gz veval
./veval version

Then hand your assistant the skill and the material to judge:

Read skills/evaluate-output/SKILL.md and use it
to evaluate my change.
Intent: <the requested outcome>
Artifacts: <files or diff to review>
Design: <relevant design documents, if available>
Criteria: <acceptance requirements>
Tests: <existing suite and execution environment, if available>
Write a report with evidence for each criterion
and distinguish checks you executed from code
inspection and supplied claims.

What comes back is a JSON report, validated by the core when veval is installed, an HTML page you can open anywhere, and a Markdown rendering for the pull request.

№ 08 — the difference

Reading the summary, or reading the work.

Trusting the descriptionv-eval
What a PASS needsThe author's wordObserved evidence with a locator a reader can follow
When the tests are missing"Probably fine"UNKNOWN, with the action that would settle it
Who computes the verdictThe reviewer's impressionOne rule, applied by the core, named in the report
A tampered testGreenA forensic finding with a benign alternative to rule out
The reportA paragraphCanonical JSON, Markdown, HTML, SARIF; content-hashed
The score7/10No composite. Counts with denominators; dimension measurements in their own units

What v-eval is not: a model leaderboard, an automatic repair loop, a hosted dashboard, or a default composite score. Those are listed as not planned in its roadmap, not missing features.

The stance

Collect everything. Show what was found. Then decide.
